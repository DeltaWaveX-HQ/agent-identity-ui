Product design · v0.1 draft · 22 Oct 2026

Agent Authorization Blueprint

How every AI agent gets its own identity, asks the user for permission, carries a short-lived pass, and is checked by a risk model before each action. This is a proposed design for the founder to edit. Numbers marked proposed are starting defaults, not tested values.

Layer 1Identity & consentOAuth 2.1 authorization server. Each agent and sub-agent gets its own short-lived, scoped token, approved by the user.
Layer 2Enforcement gatewayThe agent's only route to tools and the network. Every call is checked against the token and policy.
Layer 3Risk engineScores the agent when it asks for a token, and again on every action. High risk stops it or asks a human.

The system on one page

Enforcement gateway

  • The only route from the agent to tools and the network.
  • Checks signature, expiry, audience, DPoP proof and revocation on every call.
  • Asks policy + risk, then forwards, asks a human, or blocks.
  • Blocks unknown destinations by default (egress).

Stores

Short cache of keys and revocations (≤ 5 s).

05 · The risk model

Two models, one decision

An agent can look safe when it is created and then go too far halfway through its task. That happened in most real incidents this year. So the model scores twice: once when the agent asks for a token, and again on every action.

Model 1 · at issuance

Should this agent get a token?

Gradient-boosted trees (XGBoost) on tabular features. Fast, explainable per feature, and the same stack as an adaptive-authentication risk engine.

Budget: p95 under 50 ms proposed

Model 2 · at runtime

Should this action go through?

Rules for hard limits, plus a small sequence model over the agent's last actions to catch drift such as "kept retrying after being told no".

Budget: p95 under 30 ms at the gateway proposed

Combiner

Score → action

Rules override the score (a hard deny is always a deny). The score then picks allow, ask a human, or block and revoke.

A score is advice. The gateway is what enforces it.

How the score becomes an action

Allowscore < 0.30

Token issued or call forwarded. Logged.

Ask a human0.30 – 0.75

CIBA push to the user or owner. No answer in 2 minutes means no.

Block & revoke≥ 0.75 or any hard rule

Request denied, token family revoked, run paused, alert sent.

Thresholds are proposed. Each tenant tunes them; sensitive resources can lower the bar.

Training pipeline

Step 1Rules firstShip hand-written rules. Every decision they make becomes a labelled example.
Step 2Collect labelsThree classes: legit, rogue (legit agent that drifts), malicious. Analyst review fixes rule mistakes.
Step 3Add outside dataRed-team runs we script, plus public agent-safety benchmarks (AgentDoG, ATBench, R-Judge).
Step 4Train & testXGBoost for issuance, sequence model for runtime. Test on held-out tenants and red-team runs.
Step 5Shadow, then enforceNew model scores in shadow mode for 2 weeks, then takes over if it beats the old one.
Targets to validate
  • Precision ≥ 90% on the block tier
  • Recall ≥ 80% on red-team rogue runs
  • False blocks ≤ 1 in 1,000 legit actions
  • Revocation reaches every gateway in ≤ 5 s

proposed — measure with design partners

Publish the results

No vendor publishes independent effectiveness numbers for agent detection. We publish ours: method, data, precision, recall and false blocks per release.

Retraining

Weekly on new labels; drift alerts when the score distribution shifts; every model version is recorded on each decision for audit.

07 · Limits

What can go wrong, and what this does not do

Control plane is down

Sensitive actions fail closed. Low-risk reads use a cached decision for up to 60 s proposed. The customer chooses per resource.

Agent finds another way out

The gateway only works if it is the agent's only network route. The SDK and deployment guide lock egress; anything outside that is a known blind spot shown in the console.

Attacker's own robots

Agents run by criminals never ask us for a token. Detecting them at a victim's website is a separate, later product.

Standards are still moving

OAuth 2.1 is an IETF draft, not an RFC. We say "built on OAuth 2.1 draft-16", never "compliant", until a profile and tests exist.

Not in v1
  • Replacing the customer's login system
  • Scanning file contents
  • Local desktop agents
  • Inbound bot detection
Open decisions
  • First integration: MCP gateway or an agent SDK?
  • Host in our cloud or the customer's VPC?
  • Fail-open or fail-closed by default?
  • Which Indian bank or fintech is design partner 1?
